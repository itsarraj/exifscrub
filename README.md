# exifscrub

Views and **losslessly** strips EXIF/GPS and other metadata from JPEG
and PNG images — the camera make/model, capture timestamp, and GPS
coordinates that phone cameras embed by default, and that get
uploaded right along with the photo unless something strips them
first.

"Losslessly" is the operative word: this works at the segment/chunk
level, not by re-decoding and re-encoding the image. Every byte of
actual pixel/scan data is copied through untouched — only the
metadata containers themselves are removed.

## Installation

```sh
cargo install --path .
```

## Usage

```bash
exifscrub view photo.jpg
exifscrub view screenshot.png
exifscrub scrub photo.jpg -o clean.jpg
exifscrub scrub screenshot.png -o clean.png
```

`view` lists every metadata-carrying segment (JPEG) or chunk (PNG)
found, decoding human-readable values out of EXIF (Make, Model,
Software, DateTime, Orientation, and GPS coordinates converted to
signed decimal degrees with a ready-to-click Google Maps link) and PNG
`tEXt` chunks. `scrub` writes a new file with all of it removed and
reports exactly how many bytes were dropped.

## How it works

**JPEG**: walks the marker-delimited segment structure from SOI
through the SOS header (hand-written parser, no image-decoding
library). Segments matching APP1 (EXIF *and* XMP both live in APP1),
APP13 (Photoshop/IPTC), or COM (comments) are dropped; APP0 (JFIF),
APP2 (commonly an ICC color profile), APP14 (Adobe color-transform
marker), the quantization/Huffman tables, and — critically — every
byte of the entropy-coded scan data after SOS are copied through
verbatim. EXIF itself is parsed as a real embedded TIFF: byte-order
header, IFD0 entries (tag/type/count/value-or-offset), and a nested
GPS IFD reached via IFD0's GPSInfo pointer tag, with inline vs.
offset-indirect value storage handled per the TIFF spec's `count ×
type-size > 4 bytes` rule.

**PNG**: PNG's chunk format (4-byte length, 4-byte type, data, 4-byte
CRC) makes this simpler — metadata always lives in whole, ancillary
chunks. `tEXt`/`zTXt`/`iTXt` (text metadata), `eXIf` (the PNG spec's
own EXIF-embedding chunk, a bare TIFF blob with no `"Exif\0\0"`
prefix), and `tIME` (last-modified timestamp) are dropped; `IHDR`,
`PLTE`, `IDAT`, `IEND`, and any other chunk (e.g. `gAMA`, `sRGB`,
`pHYs`) are kept byte-for-byte, CRC included.

## Status: built, unit-tested, and live-verified against real Pillow-generated images with independent cross-checking

- **20 unit tests** (`cargo test --lib`) cover JPEG segment parsing
  (SOI detection, stopping at SOS, malformed-file rejection), the full
  TIFF/EXIF IFD parser (ASCII tags both inline and offset-indirect,
  inline SHORT values, a hand-built nested GPS IFD with hemisphere-sign
  handling verified to 6 decimal places, big-endian `"MM"` byte order),
  metadata stripping (removes APP1/COM, preserves entropy-coded scan
  data and EOI byte-for-byte, is a true no-op on a file with none), and
  the equivalent PNG chunk suite (finds IHDR/IDAT/IEND, stops at IEND
  even with trailing garbage, strips tEXt/zTXt/iTXt/eXIf/tIME while
  preserving IDAT exactly, decodes tEXt keyword/value). **Two real
  fixture bugs caught by the tests themselves**: a clippy
  `identity_op` lint on a `1 * 12` test-offset computation, and — more
  substantively — a hand-built minimal-JPEG test fixture whose fake DQT
  segment declared a 3-byte payload in its length field but only
  supplied 2 payload bytes, desyncing the segment parser one byte early
  and causing every subsequent marker lookup to fail. Fixed the test's
  malformed fixture bytes, not the (correctly strict) parser that
  caught the desync.
- **Live-verified against real image files generated by Pillow 12.3.0**
  (not hand-crafted bytes) **and cross-checked by Pillow's own,
  independent EXIF/PNG reader** rather than trusting this tool's own
  output:
  - A real 64×48 JPEG with a real embedded EXIF block (Make, Model,
    Software, DateTime, Orientation, and a real nested GPS IFD: `37°
    46' 30" N, 122° 25' 10" W`). `exifscrub view` decoded every field;
    Pillow's `Image.getexif()` / `get_ifd(GPSInfo)` on the same file
    returned identical raw values, and this tool's decimal-degree
    conversion (`37.775000, -122.419444`) matches the hand-computed
    DMS→decimal conversion of Pillow's raw tuples exactly.
  - `exifscrub scrub` on that file: removed exactly 266 bytes (the
    full APP1 segment), and **Pillow re-opening the scrubbed file
    reports an empty EXIF dict** (`{}`) — independent confirmation the
    metadata is actually gone, not just unlisted by this tool's own
    viewer. Pixel data compared via `list(img.getdata())` on both
    files: **identical**, confirming the strip was truly lossless.
  - A real 32×24 PNG with three real Pillow-written `tEXt` chunks
    (Author, Description, Software). `exifscrub view` correctly listed
    and decoded all three; `exifscrub scrub` removed exactly 139 bytes,
    and **Pillow re-opening the scrubbed PNG reports `img.text == {}}`**
    — independently confirmed empty — with pixel data again verified
    bit-identical between original and scrubbed files.

**Not done / deliberately deferred**: no PDF support (PDF metadata
lives in a very different structure — the `/Info` dictionary and
optional XMP streams inside an object graph with a cross-reference
table — out of scope for this pass; JPEG and PNG cover the large
majority of real-world photo/screenshot privacy-leak cases); no WebP,
HEIC/HEIF, or TIFF container support; XMP metadata that happens to
share JPEG's APP1 marker is stripped along with EXIF (both use APP1)
but isn't separately parsed/displayed, only EXIF's TIFF structure is
decoded for `view`; no CRC recomputation for PNG (unaffected — chunks
are only ever fully kept or fully dropped, never modified in place, so
every surviving chunk's original CRC stays valid).
